# Well Model Builder — описание проекта и контекст для ИИ

> Этот файл — вводный бриф для другого ИИ-разработчика. Сначала прочитай его, затем `README.md` и соответствующие исходники. Считай текущий код главным источником истины, если детали ниже с ним расходятся.

## Коротко о продукте

**Well Model Builder** — веб-приложение для узлового анализа добывающей нефтяной скважины. Оно рассчитывает приток из пласта (**IPR**), гидравлический подъём флюида (**VLP**) и находит их пересечение — рабочую точку `(q_liq, p_wf)`. Пользователь вводит параметры скважины, выбирает пресет, запускает расчёт, изучает кривые и дополнительные инженерные инструменты. В интерфейсе предусмотрен ИИ-ассистент, который может объяснять методику и помогать работать с расчётами; численный результат должен подтверждаться расчётным ядром, а не выдумываться моделью.

Проект создан для нефтегазового инженерного сценария и хакатона. Основной язык интерфейса — русский. Это инженерная рабочая система, а не маркетинговый лендинг.

## Что должно делать приложение

1. Принимать структурированные параметры пласта, заканчивания, PVT и инклинометрии.
2. Строить кривые притока IPR и подъёма VLP.
3. Находить рабочую точку пересечения кривых либо явно показывать, что пересечения нет.
4. Показывать численные результаты и график с понятными единицами измерения.
5. Позволять менять параметры и выбирать готовые пресеты.
6. Давать доступ к дополнительным операциям: what-if, оптимизация, сверка с полевым замером, пакетный расчёт, распознавание файла/фото, аудио, экспорт отчётов, протокол совещания и локальная база методик.
7. Быть удобным на desktop и мобильном экране, не иметь горизонтального переполнения и сохранять читаемость инженерных данных.

## Архитектура

Микросервисная архитектура: React/Vite frontend → FastAPI backend-оркестратор → три расчётных HTTP-сервиса.

```text
Браузер :3000
   │ /api/* через nginx
   ▼
FastAPI backend :8080
   ├── IPR service :8003   — приток из пласта
   ├── VLP service :8002   — PVT + многофазный подъём
   └── Nodal service :8004 — пересечение полилиний
```

## Расчётная методика

- **IPR:** Composite IPR Brown (1984). Линейный приток над давлением насыщения и кусочная двухфазная модель при давлении ниже `pb`; нефть по Vogel, вода по Darcy.
- **PVT Black Oil:** Standing для свойств насыщенной нефти, Vasquez–Beggs для недонасыщенной нефти, Beggs–Robinson для вязкости нефти, корреляции для газа; вода моделируется как несжимаемая.
- **VLP:** двухсекционная конструкция НКТ/эксплуатационная колонна; трение Colebrook–White; численное интегрирование давления RK45 с fallback RK23; температурный профиль использует TVD.
- **Nodal:** геометрическое сегментное пересечение двух полилиний в координатах `(q_liq, p_wf)`.
- Единицы и точные ограничения смотри в Pydantic схемах соответствующих сервисов и в `README.md`.

## Основные API-контракты

- `POST /api/calculate` — полный расчёт IPR/VLP/Nodal; возвращает кривые и `operating_point`, либо отсутствие рабочей точки.
- `GET /api/presets`, `GET /api/presets/{id}` — готовые входные наборы.
- `GET /api/health`-подобный статус: backend `GET /health`, AI `GET /api/chat/status`.
- `POST /api/chat` и `/api/chat/upload` — чат и разбор файлов.
- `POST /api/enhancements/*` — 12 дополнительных инструментов. Перечень, поля и ответы смотри в `docs/FRONTEND_INTEGRATION.md`, OpenAPI и `frontend/src/api/client.ts`.
- UI использует относительные `/api/*`; nginx проксирует их к backend. Не хардкодить hostname Docker в браузерном клиенте.
- Для нового API: добавь/обнови TypeScript-тип, метод в `client.ts`, пользовательское состояние/feedback и доступный UI; проверяй реальный backend contract, а не только пример в docs.

## Дополнительные возможности

В актуальной ветке интегрированы инструменты из презентации:

1. What-if сценарии через ассистента.
2. Vision/OCR паспорта скважины, загрузка/камера/вставка изображения — конкретные действия смотри в текущем коде.
3. Голосовой ввод/ГС: браузерная запись и/или аудиофайл, отправка на транскрибацию и возможность применить извлечённые параметры.
4. Импорт `.txt`, `.csv`, `.json`, `.xlsx`, `.docx`, `.pdf`.
5. Экспорт отчёта HTML, Excel, CSV, JSON и Markdown.
6. Сканирование папки `samples`.
7. Prompt-injection guardrails и контроль недостоверных чисел.
8. Локальный RAG по методике.
9. Оптимизация НКТ, устьевого давления, критического WCT.
10. History matching фактического замера.
11. Протокол технического совещания.
12. Пакетный расчёт фонда и сводный Excel.

Важно: не обещай и не показывай пользователю результат, если конкретный backend режим его не вернул. Визуальная загрузка файла сама по себе не означает, что файл автоматически изменил параметры: UI должен явно показать, что распознано и что применено.

## Дизайн / UX требования

- Это **рабочее инженерное приложение**: график и рабочая точка — центральный объект, параметры и инструменты должны быть доступны без лишних шагов.
- Пользователь недавно запросил **10 действительно разных вариантов интерфейса**, не просто смену темы. Текущий frontend имеет верхний переключатель и хранит выбранный вариант в query `?design=1..10`. Перед добавлением UI сначала проверь, что все 10 вариантов остаются достижимы и имеют осмысленно разные компоновки.
- Текущая основная визуальная концепция — Swiss/instrument-sheet; она не должна насильно подменять остальные 9 концепций.
- Ассистент должен быть **отдельно открываемым компактным floating-widget**, а не постоянно занятой колонкой. Он раскрывается по действию, не затемняет всю страницу без необходимости, умеет закрываться/сворачиваться; сообщения доступны с прокруткой. Учитывай свежие upstream changes, но не ломай эту модель без прямого запроса пользователя.
- Не вводить большие пустые боковые поля: рабочая область должна использовать viewport, с небольшими только необходимыми gutters. На desktop — широкая рабочая поверхность, на мобильном — адаптивный вертикальный поток.
- Не урезать инженерные поля или результат ради визуального упрощения; поддерживать параметры, единицы, график, состояние ошибки/нет пересечения и расширенные инструменты.
- Русский язык UI. Никаких случайных английских placeholder-копирайтов, декоративных emoji как системных иконок, фиктивных инженерных чисел.
- Доступность: видимый focus, labels у форм, клавиатурное управление, достаточный контраст, `prefers-reduced-motion`, сообщение ошибок рядом с действием.

## Проверка и команды

```bash
# Frontend: TypeScript + production build
cd frontend && npm run build

# Проверка Compose
cd .. && docker compose config --quiet

# Полная локальная система
docker compose --profile app up -d --build

# Состояние сервисов
docker compose ps

# Основные проверки API
curl http://localhost:8080/health
curl http://localhost:8080/docs
curl http://localhost:8002/vlp/health
curl http://localhost:8003/ipr/health
curl http://localhost:8004/nodal/health
```
